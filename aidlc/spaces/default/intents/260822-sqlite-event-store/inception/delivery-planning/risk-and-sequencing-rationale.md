# 順序づけの根拠 (risk-and-sequencing-rationale)

「Bolt」は設計〜実装〜テストを一気に通す1回のビルドパス。Bolt計画（`bolt-plan.md`）の順序（スケルトン→本実装→CI/ドキュメント）の根拠を記録する。

## 採用ヒューリスティック

**ウォーキングスケルトン先行（Cockburn）＋リスク先行（Boehm）** の複合。ウォーキングスケルトンとは、全レイヤを貫いて動く最小版を最初に作り、部品がつながることを実機能の前に証明するやり方。形式的なスコアリングモデル（WSJF等 — 価値・緊急度をサイズで割って順位づけする方式）は、Bolt数が3と少なく順序が依存関係でほぼ決まるため採用しない。

## 順序の論拠

1. **Bolt 1（スケルトン）が最初**: このビルドの最大の不確実性は (a) rusqliteのspawn_blocking非同期化が既存のasyncトレイト契約と噛み合うか（RAIDログ A1/A2）、(b) 中立エラー型への再設計が既存3バックエンドを壊さないか（TD-01）。両方をBolt 1の薄い1本で最初に検証する — リスク先行方針（範囲定義Q4）とチームプラクティスのスケルトンスタンス（両方とも確定事項）の直接適用
2. **Bolt 2が本体**: スケルトンで証明済みの土台の上に、feature分割の完成と全機能・全テストを載せる。ユニット依存DAG（`../units-generation/unit-of-work-dependency.md`: U1→U2）のトポロジーに整合
3. **Bolt 3が最後**: CIマトリクス（U3）は全featureの存在が前提、ドキュメント（U4）は最終APIとスキーマが確定してから — DAGの末端（U3/U4）をまとめて1 Boltに。直列実行の確定（Q2=A）によりU3/U4の並行機会は使用しない

## トポロジカル順序からの逸脱

ユニット単位のトポロジカル順序（U1完結→U2完結→U3/U4）に対し、Bolt 1がU1とU2を薄く横断する点が唯一の逸脱。逸脱の正当化: スケルトンの目的（レイヤ貫通の証明）はU1だけでは達成できず、SQLiteの最小スライスまで含めて初めて「土台がつながる」ことを示せる。ユニットの完結性はBolt 2で回復する（U1・U2ともBolt 2完了時点で完結）。

## リスク対応の位置づけ

| リスク（RAIDログ） | 対応Bolt |
|---|---|
| A1/A2（ドライバ・トレイト適合の前提） | Bolt 1で検証・解消 |
| R5（楽観的ロックの競合条件） | Bolt 2（競合パステスト必須 — チームプラクティス確定） |
| R2（CIマトリクスの組み合わせ増） | Bolt 3（代表組み合わせに絞る設計） |
| R4（破壊的変更の利用者影響） | Bolt 3（移行手順・CHANGELOG） |
