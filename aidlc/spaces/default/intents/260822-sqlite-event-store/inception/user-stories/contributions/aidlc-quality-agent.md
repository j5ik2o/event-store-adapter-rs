## Contribution

テスト容易性（各ACの合否判定可能性）の観点でドラフトの全ACを検分した。全体としてACはFRへ正しくトレースされ、必須の楽観的ロック競合パス（AC1.2.1）とエラー契約（AC2.2.1 / AC2.2.2 / AC3.2.3）はストーリー面に載っている。以下は合否判定を一意にするための指摘である。

### 重要指摘（実行不能・判定不能のリスク）

1. **AC2.2.2「4バックエンドすべてが同一のエラー表現を返す」は実行時検証不能** — DynamoDB / Bigtable で楽観的ロック競合をCI上で実際に発生させるテストは、team-practices 自身が「既存バックエンドでは書けなかった」と認める種類のものであり、このAC文面のままでは実行できないテストがMustに残る。ランタイム検証は sqlite + memory に限定し、dynamodb / bigtable 側は「エラー型定義にSDK型が含まれない」型レベル検証（コンパイル検査・レビュー）へ分割して書き直すべき。

2. **SQLite固有のエラー写像のサッドパスACが欠落** — construction ガードレール（ハッピーパス＋エラー/エッジ2件以上）と NFR-4（panic禁止・`EventStoreWriteError` / `EventStoreReadError` への写像）に対し、SQLite側のIO/SQLエラー系ACが存在しない。現在のサッドパスは競合（AC1.2.1）と Memory の panic 修正（AC3.1.1）のみで、team-practices Q4 が必須とするエラー契約回帰テスト（(2) persist_event の呼び出し契約）の書き起こし先が AC3.2.3 のメタ記述しかない。追加提案: 「Given 書き込み不能な接続先（存在しないディレクトリ・読み取り専用ファイル等） When `persist_event` を呼ぶ Then panic せず `EventStoreWriteError` が返る」を US2.2 または US3.2 のACとして明記する。

3. **AC2.3.1「クリーンな環境（システムSQLiteなし）」の検証手順が未定義** — GitHub Actions ランナー上のシステムSQLiteの有無は制御されておらず、このままでは偶然パス（vacuous pass）しうる。合否を一意にする案: (a) libsqlite3-dev を持たないコンテナ（または明示的アンインストール後）のジョブでバンドルビルドを行う、(b) 生成バイナリが libsqlite3 に動的リンクしていないことを `ldd` / `otool` で検査する。対の AC2.3.2「同梱コンパイルなし」も直接観測が難しいため、`cargo tree -e features` で libsqlite3-sys の `bundled` feature が無効であることの検査を合格条件にするのが決定的。

4. **AC1.4.2（delete_ttl）の駆動系と時間制御が未指定** — 「保守処理が動く」では、いつ・何が削除を駆動するのか判定できない。またTTL経過を実時間 sleep で作るテストは NFR-5（決定的）に反する。削除トリガー（書き込み時に付随か、明示的な保守APIか）と時間戦略（注入クロック、またはTTL=0の境界値）をACに固定すること。

### 中程度の指摘（曖昧さの解消）

5. **AC1.2.1「2つの並行更新」の決定的な構成を明記** — タスクを実際にレースさせるテストはフレーキになりうる。「同一バージョンの集約を2回ロードし、順に2回コミットする → 2回目が `OptimisticLockError` を受け取る」という決定的構成で検証可能であることをAC文面（または注記）に落とすべき。NFR-5（決定的・並列安全）とも整合する。

6. **AC1.2.2（原子性）は外形観測が困難** — 「単一トランザクションで原子的」は実行時テストの合否として直接観測できない実装特性。観測可能な帰結（競合に敗れた側の試行後、journal に部分的な行が残らない／version が二重に進まない）へ言い換えるか、設計レビューで確認するACである旨を明記すること。

7. **AC1.3.1（`:memory:`）の共有範囲** — 「同一インスタンスで整合」は先行レビュー指摘（requirements.md Finding 1）への回答として方向は妥当。ただし rusqlite の `:memory:` はコネクション単位で別DBになるため、テストが「インスタンス内で複数操作を跨いでもデータが見える（内部実装が複数コネクションでも成立する）」ことを検証する意図を明示すべき。また「別インスタンス間での `:memory:` 共有は保証しない（スコープ外）」の一文があると境界の合否が定まる。

8. **検査系AC（AC1.1.3 / AC3.1.2 / AC2.1.4 / AC3.1.3 / AC3.2.2）は検証手段を注記** — これらは実行時テストではなく、コンパイル時検査または機械的走査で判定する: `StorageBackend` 実装はトレイト境界のコンパイル時アサーション（例: `fn assert_impl<T: StorageBackend>()`）、`unsafe impl` / `#[allow(dead_code)]` / testcontainers 参照の不在は grep 走査（AC3.1.3 は新規ファイル群にスコープを限定 — 既存3バックエンドには `unsafe impl` が残るため全体走査では常に失敗する）。手段を注記しないと「レビューで見た」だけの常時パスACに退化する。

9. **AC1.4.3 は単独では常時パスになりうる** — 「設定が実際に効く」は、AC1.4.1 / AC1.4.2 の Then が DB の実状態（snapshot テーブルの行数・内容）を assert すれば自動的に満たされるメタ記述。独立ACとせず 1.4.1 / 1.4.2 の Then を強める形に統合するのが安全。なお実状態 assert の明記は、既知欠落「DynamoDB テストは `with_keep_snapshot_count` を設定するだけで結果未検証」の再発防止としても価値がある。

### 軽微

10. AC2.1.1 / AC2.1.3 の `cargo tree` 判定は、CI実装時にエッジ指定（`-e normal` 等でdev依存を除外）を固定すること。dev依存経由の偽陽性を防ぐ。
11. AC3.3.3 の「定期実行またはPR時」は「または」で合否が割れる。team-practices Q8 の決定（既存日次cronへの相乗り）に合わせトリガーを1つに固定する。
12. AC4.1.2（examples 実行）はCI外の手動検証である旨を注記する。examples のCIビルド検証はバックログ確定（team-practices）のため、ACがその決定と矛盾しない形にしておく。
13. NFR-1（公開トレイトシグネチャ不変更）に対応するACがない。cargo-semver-checks 導入かレビュー確認かは後続工程の判断でよいが、検証先の所在は traceability に一言残すべき。
