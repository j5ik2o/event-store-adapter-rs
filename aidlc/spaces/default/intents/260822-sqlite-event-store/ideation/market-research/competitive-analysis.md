# 競合分析: SQLite対応EventStoreとバックエンドfeature分割

本書はインテントステートメント（`../intent-capture/intent-statement.md`、intent-statement）を前提に、市場調査Q&A（`market-research-questions.md`）の確認済み回答に基づいて作成した。

## ポジショニング方針

- 本ライブラリは競合クレートとの機能競争を目的とせず、event-store-adapter-* ファミリー（多言語展開）の思想に基づく自分のエコシステム向けライブラリとして位置づける。競合比較は参考情報にとどめる（Q1回答）。
- 中核となる差別化ポイントは「**アクターモデルを前提とせずに CQRS/イベントソーシングを実現できること**」である（Q2回答）。重量級のCQRS/ESフレームワークやアクターランタイムを導入せずに、リポジトリ実装の内側で使える軽量アダプタという立ち位置を維持する。

## 参考: 周辺のRustイベントソーシング系クレート

競合比較を行わない方針（Q1回答）のため、以下は深掘りしない参考情報である。cqrs-es / esrs / eventually / thalo などのクレートが存在するが、多くはフレームワーク型（アグリゲート定義やランタイムへの組み込みを要求する）であり、本ライブラリの「アダプタに徹する」方針とはアプローチが異なる（この段落の周辺クレートに関する記述は詳細調査を行っていない参考レベルの認識である）。

## 利用者が期待するテーブルステークス

SQLite対応において利用者が「当然あるもの」と期待する事項（Q3回答・全項目選択）:

| 期待事項 | 内容 |
|---|---|
| 単一ファイルDB・組み込み動作 | サーバプロセス不要。`:memory:` モードを含む |
| 同一トレイト/API | コード変更なしで既存バックエンドと切替可能 |
| マイグレーション | テーブル自動作成またはスキーマDDLの提供 |
| 既存機能との完全互換 | 楽観的ロック・スナップショットが既存バックエンドと同様に動く |

これらは差別化要素ではなく最低条件として扱う。
